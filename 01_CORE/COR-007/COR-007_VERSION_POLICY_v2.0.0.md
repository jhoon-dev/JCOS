# 1. 목적과 비목적

## 1.1 목적

버전 정책의 목표는 어떤 기준이 언제 왜 바뀌었고, 누가 검토·승인했으며, 현재 어떤 버전과 상태를 사용해야 하는지 명확하게 하는 것이다.

## 1.2 비목적

이 문서는 개별 변경의 우열·충돌·예외 판단, 파일 전달 절차, 저장소 명령, 배포 자동화와 채널별 발행 운영을 정의하지 않는다.

## 1.3 결과 기준

좋은 버전 관리는 번호, 상태, 변경 내용, 호환성, 승인 근거, 기준본과 대체 관계가 서로 일치하고 과거 상태를 재현할 수 있다.

# 2. 적용 범위와 책임

## 2.1 적용 대상

Foundation, Core, Design, Content, Automation, Project 문서와 규칙 세트, 템플릿, 패키지, 스키마와 승인된 기준 산출물에 적용한다.

## 2.2 작성자 책임

작성자는 변경 내용을 분리하고 영향과 호환성을 평가하며 적절한 버전·상태 제안과 변경 기록을 준비한다.

## 2.3 검토자 책임

검토자는 변경 범위, 버전 증가, 관련 문서 정합성, QA 결과와 마이그레이션 영향을 확인한다.

## 2.4 승인자 책임

승인자는 승인 권한 범위 안에서 상태 전환, 예외, LOCKED 또는 폐기를 명시적으로 결정하고 근거를 남긴다.

# 3. 상위 규칙과 인접 문서

## 3.1 COR-001 상속

사용자 승인, 기존 파일 보존, 범위 통제, 상위 규칙 우선과 실패 보고는 COR-001을 상속한다.

## 3.2 COR-005 연결

APPROVED 또는 LOCKED 후보는 해당 버전에 대한 품질 게이트와 증거를 COR-005에 따라 통과해야 한다.

## 3.3 COR-006 연결

버전별 파일명, 패키지, 무결성 검증값과 전달 기록은 COR-006을 따른다.

## 3.4 COR-008 경계

규칙 충돌, 예외 허용, 불확실성과 선택지 판단은 COR-008에서 정의한다.

# 4. 버전 식별 체계

## 4.1 기본 형식

정식 버전은 Major.Minor.Patch의 세 자리 숫자로 표시하고 각 구성요소는 0 이상의 정수로 관리한다.

## 4.2 문서 ID와 버전

문서 ID는 책임 단위를 식별하고 버전은 같은 책임 단위의 변경 이력을 식별한다. 의미와 책임이 크게 달라지면 새 문서 ID를 검토한다.

## 4.3 사전 릴리스

정식 승인 전 시험 배포가 필요하면 alpha, beta, rc 등 사전 릴리스 라벨을 버전 뒤에 추가하고 정식본보다 낮은 우선순위로 본다.

## 4.4 빌드·해시

같은 버전의 정확한 파일을 구분해야 할 때 빌드 식별자, 생성 시각 또는 SHA-256을 함께 기록한다.

# 5. 변경 분류와 버전 증가

## 5.1 Major

호환되지 않는 책임·구조·규칙 의미 변경, 기존 사용자의 필수 마이그레이션 또는 대규모 재설계는 Major를 증가시킨다.

## 5.2 Minor

기존 호환성을 유지하는 새 기능·규칙·섹션·선택적 기능 추가와 의미 있는 확장은 Minor를 증가시킨다.

## 5.3 Patch

의미와 호환성을 바꾸지 않는 오류 수정, 명확화, 오탈자, 링크·메타데이터·렌더링 보정은 Patch를 증가시킨다.

## 5.4 누적 변경

한 릴리스에 여러 변경이 있으면 가장 큰 영향의 변경 분류를 버전 증가에 적용한다.

# 6. 상태 수명주기

## 6.1 DRAFT

작성 중이며 구조와 내용이 바뀔 수 있고 운영 기준으로 사용할 수 없는 상태다.

## 6.2 REVIEW

내용과 형식이 검토 가능한 수준이며 피드백과 수정이 진행 중인 상태다.

## 6.3 APPROVED

지정 승인자가 해당 버전의 내용과 사용을 승인했으나 실전 검증이나 LOCKED 조건이 남을 수 있는 상태다.

## 6.4 LOCKED

필요한 승인과 실전 검증을 완료해 운영 기준으로 고정되며 승인 없는 의미 변경을 금지하는 상태다.

## 6.5 DEPRECATED

대체본이 있거나 사용 중단이 결정되어 새 작업에는 권장하지 않지만 기존 참조를 위해 유지되는 상태다.

## 6.6 ARCHIVED

운영 사용을 종료하고 이력·감사 목적으로만 보존하는 상태다.

# 7. 변경 요청과 영향 평가

## 7.1 변경 요청

변경 요청에는 대상, 현재 버전·상태, 문제, 제안, 이유, 범위와 요청자를 기록한다.

## 7.2 영향 분석

규칙, 문서, 템플릿, 프로젝트, 자동화, 데이터, 교육과 전달 패키지에 미치는 직접·간접 영향을 평가한다.

## 7.3 호환성

기존 입력·출력·참조·프로젝트가 그대로 동작하는지, 변경이나 마이그레이션이 필요한지 판정한다.

## 7.4 변경 묶음

서로 독립적인 변경은 분리하고, 같은 목적과 승인·롤백 단위를 공유하는 변경만 하나의 릴리스로 묶는다.

# 8. 검토와 승인

## 8.1 검토 증거

검토에는 변경 전후, QA 결과, 열린 결함, 호환성, 마이그레이션, 보안과 잔여 위험을 포함한다.

## 8.2 승인 권한

상태 전환은 문서·프로젝트의 지정 소유자 또는 위임받은 승인자가 수행한다.

## 8.3 명시적 승인

침묵, 파일 전달, 회의 참석 또는 사용 시작을 승인으로 간주하지 않으며 승인 대상 버전과 상태를 명시해야 한다.

## 8.4 조건부 승인

조건부 승인은 잔여 항목, 책임자, 기한, 사용 제한과 재검토 조건을 기록하며 LOCKED를 자동 허용하지 않는다.

# 9. LOCKED 통제

## 9.1 진입 조건

LOCKED는 APPROVED, Critical 결함 0건, 필요한 실제 적용, 기준본·의존성 정합성과 명시적 승인 후에만 허용한다.

## 9.2 변경 금지

LOCKED 파일·규칙·템플릿은 승인된 변경 요청과 새 버전 없이 내용이나 의미를 수정하지 않는다.

## 9.3 잠금 해제

LOCKED 기준을 변경하려면 영향 분석, 새 버전, QA와 승인 절차를 시작하며 기존 잠금본은 이력으로 보존한다.

# 10. 릴리스와 기준본

## 10.1 기준본

각 책임 단위와 적용 범위에는 현재 사용해야 할 하나의 기준 버전과 상태를 등록한다.

## 10.2 릴리스 후보

정식 전 최종 검증본은 rc로 표시할 수 있으며 승인 전 기준본을 대체하지 않는다.

## 10.3 릴리스 패키지

릴리스에는 본문, 변경 이력, QA 증거, 의존성, 마이그레이션 안내, 검증값과 알려진 제한을 필요한 만큼 포함한다.

## 10.4 동시 버전

여러 버전을 병행 지원하면 적용 대상, 지원 기간, 차이와 종료 조건을 명시한다.

# 11. 호환성·마이그레이션·의존성

## 11.1 호환성 범위

문서 참조, 규칙 ID, 스키마, 입력·출력, 템플릿과 자동화 인터페이스의 호환성을 평가한다.

## 11.2 마이그레이션

기존 사용자가 변경해야 하는 항목, 순서, 검증, 롤백과 지원 기간을 실행 가능한 안내로 제공한다.

## 11.3 의존성 정합

상위·하위 문서와 프로젝트가 참조하는 버전 범위를 확인하고 호환되지 않는 조합을 기준본으로 승인하지 않는다.

# 12. 폐기·보관·롤백

## 12.1 폐기

DEPRECATED에는 대체 버전, 폐기 이유, 전환 기한과 남은 지원 범위를 표시한다.

## 12.2 보관

ARCHIVED에는 최종 상태, 효력 종료일, 대체본과 이력 위치를 기록하고 운영 기준에서 제거한다.

## 12.3 롤백

롤백은 알려진 정상 버전으로 되돌리는 통제된 릴리스이며 대상, 이유, 영향, 데이터·호환성, QA와 승인 기록을 남긴다.

## 12.4 긴급 수정

긴급 수정도 임시 변경을 숨기지 않고 버전, 영향, 최소 QA, 승인과 후속 정규화를 기록한다.

# 13. 기록과 감사

## 13.1 변경 이력

각 버전은 날짜, 작성자, 변경 분류, 변경 내용, 이유, 관련 요청과 상태를 기록한다.

## 13.2 승인 기록

승인 기록은 정확한 버전·해시, 승인자, 시각, 승인 상태, 조건과 근거에 연결한다.

## 13.3 기준본 등록부

현재 기준본, 지원 버전, 폐기·보관 버전과 적용 대상을 하나의 등록부에서 추적한다.

# 14. 규칙 카탈로그

이 장의 규칙은 규범적이다. Project Module은 필요한 VER Rule ID를 참조하고, 프로젝트 특수 버전 기준은 프로젝트 전용 Rule ID로 확장한다.

## 14.A 식별과 기준선 (VER-001 ~ VER-005)

### VER-001 - 버전 필수
- **Priority:** Critical
- **Statement:** 관리 대상 문서, 규칙 세트, 템플릿과 릴리스 패키지에는 식별 가능한 버전을 부여해야 한다.
- **Rationale:** 버전이 없으면 변경 전후와 적용 기준을 구분할 수 없다.
- **Verification:** 등록 대상의 메타데이터와 파일명을 확인한다.
- **Exceptions:** 일회성 작업 메모는 DRAFT와 생성 시각으로 식별할 수 있다.

### VER-002 - 세 자리 버전 형식
- **Priority:** Critical
- **Statement:** 정식 버전은 Major.Minor.Patch 세 구성요소의 정수 형식으로 기록해야 한다.
- **Rationale:** 일관된 형식은 비교와 자동 처리를 가능하게 한다.
- **Verification:** 버전 문자열과 메타데이터를 형식 검사한다.
- **Exceptions:** 사전 릴리스와 빌드 라벨은 정식 버전 뒤에 추가할 수 있다.

### VER-003 - 문서 ID와 버전 분리
- **Priority:** High
- **Statement:** 책임 단위를 나타내는 문서 ID와 같은 단위의 변경을 나타내는 버전을 구분해야 한다.
- **Rationale:** 버전 변경마다 새 ID를 만들거나 다른 책임을 같은 ID에 넣는 혼선을 막는다.
- **Verification:** Document Register와 버전 이력을 대조한다.
- **Exceptions:** 책임 자체가 분리·통합되면 새 ID와 대체 관계를 정의한다.

### VER-004 - 상태 식별
- **Priority:** Critical
- **Statement:** 각 관리 버전에는 DRAFT, REVIEW, APPROVED, LOCKED, DEPRECATED 또는 ARCHIVED 상태를 하나만 표시해야 한다.
- **Rationale:** 동일 버전의 상태가 모호하면 사용 가능 여부를 판단할 수 없다.
- **Verification:** 파일, 본문, 등록부와 릴리스 기록의 상태를 비교한다.
- **Exceptions:** 상태 변경 이력에는 과거 상태를 시간순으로 보존한다.

### VER-005 - 정확한 대상 해시
- **Priority:** High
- **Statement:** 승인·LOCKED·전달 기록은 가능한 경우 정확한 파일 또는 패키지 해시에 연결해야 한다.
- **Rationale:** 같은 이름과 버전의 다른 바이트에 승인이 잘못 적용될 수 있다.
- **Verification:** 기록된 SHA-256과 실제 대상을 비교한다.
- **Exceptions:** 변동형 시스템은 불변 리비전 ID와 생성 시각으로 대체할 수 있다.

## 14.B 변경 분류와 증가 (VER-006 ~ VER-010)

### VER-006 - Major 증가
- **Priority:** Critical
- **Statement:** 호환되지 않는 규칙 의미, 책임, 구조 또는 필수 사용 방식 변경은 Major를 증가시켜야 한다.
- **Rationale:** 기존 사용자가 그대로 적용할 수 없는 변경을 명확히 경고한다.
- **Verification:** 호환성·마이그레이션 평가와 버전 증가를 대조한다.
- **Exceptions:** 실험 DRAFT는 정식 증가 전 사전 릴리스로 관리할 수 있다.

### VER-007 - Minor 증가
- **Priority:** Critical
- **Statement:** 기존 호환성을 유지하는 새 규칙, 기능, 섹션 또는 선택적 확장은 Minor를 증가시켜야 한다.
- **Rationale:** 의미 있는 기능 추가를 단순 수정과 구분한다.
- **Verification:** Change Log의 Added 항목과 버전 번호를 확인한다.
- **Exceptions:** 문서 책임을 바꾸는 확장은 Major 또는 새 문서 ID를 검토한다.

### VER-008 - Patch 증가
- **Priority:** High
- **Statement:** 의미와 호환성을 유지하는 오류 수정, 명확화, 오탈자와 형식 보정은 Patch를 증가시켜야 한다.
- **Rationale:** 작은 변경도 과거 파일과 구분하고 추적해야 한다.
- **Verification:** 변경 전후 의미·인터페이스와 Patch 증가를 확인한다.
- **Exceptions:** 승인 전 같은 DRAFT 작업 세션의 중간 저장은 별도 Patch를 만들지 않을 수 있다.

### VER-009 - 최대 영향 적용
- **Priority:** Critical
- **Statement:** 한 릴리스에 여러 변경 분류가 있으면 가장 큰 호환성 영향을 버전 증가에 적용해야 한다.
- **Rationale:** 작은 수정이 함께 있다는 이유로 파괴적 변경을 낮게 표시하면 안 된다.
- **Verification:** 모든 변경의 분류와 최종 증가 수준을 비교한다.
- **Exceptions:** 독립 릴리스로 분리하면 각 변경 묶음에 별도 버전을 적용한다.

### VER-010 - 버전 재사용 금지
- **Priority:** Critical
- **Statement:** 전달·승인·공개된 버전 번호를 다른 내용에 재사용하거나 덮어쓰지 않는다.
- **Rationale:** 불변성이 깨지면 승인, 해시와 이력을 신뢰할 수 없다.
- **Verification:** 동일 버전의 과거·현재 해시를 비교한다.
- **Exceptions:** 잘못 생성된 미전달 DRAFT는 기록 후 폐기하고 새 빌드로 교체할 수 있다.

## 14.C 상태 수명주기 (VER-011 ~ VER-015)

### VER-011 - DRAFT 운영 금지
- **Priority:** Critical
- **Statement:** DRAFT를 승인된 운영 기준이나 최종 사용자 전달본으로 사용하지 않는다.
- **Rationale:** 작성 중 내용은 검토 없이 바뀔 수 있다.
- **Verification:** 운영 등록부와 전달 기록에 DRAFT가 없는지 확인한다.
- **Exceptions:** 중간 피드백 요청은 DRAFT임을 명시해 제한적으로 공유할 수 있다.

### VER-012 - REVIEW 진입 조건
- **Priority:** High
- **Statement:** 구조와 필수 내용이 갖춰지고 검토 가능한 대상이 고정된 뒤 REVIEW로 전환해야 한다.
- **Rationale:** 미완성 조각을 최종 검토에 올리면 피드백 비용이 증가한다.
- **Verification:** Entry Checklist와 대상 버전·해시를 확인한다.
- **Exceptions:** 구조 검토용 조기 REVIEW는 목적과 미완성 범위를 표시한다.

### VER-013 - APPROVED 명시성
- **Priority:** Critical
- **Statement:** APPROVED는 지정 승인자가 정확한 버전과 범위를 명시적으로 승인한 경우에만 부여한다.
- **Rationale:** 침묵이나 사용 시작은 승인 의사를 보장하지 않는다.
- **Verification:** 승인자, 시각, 대상과 승인 문구를 확인한다.
- **Exceptions:** 없음.

### VER-014 - LOCKED 진입 조건
- **Priority:** Critical
- **Statement:** LOCKED는 APPROVED, 필수 QA 통과, 필요한 실제 적용과 명시적 잠금 승인을 모두 충족해야 한다.
- **Rationale:** 잠금은 운영 기준의 안정성과 변경 통제를 의미한다.
- **Verification:** Lock Checklist의 승인·QA·적용 증거를 확인한다.
- **Exceptions:** 없음.

### VER-015 - 폐기 상태 분리
- **Priority:** High
- **Statement:** 대체 후 제한 사용 중인 버전은 DEPRECATED, 운영 사용을 종료한 이력본은 ARCHIVED로 구분해야 한다.
- **Rationale:** 폐기 단계에 따라 허용되는 사용과 지원 범위가 다르다.
- **Verification:** Registry의 상태, 대체본과 지원 종료일을 확인한다.
- **Exceptions:** 즉시 사용 금지가 필요한 버전은 DEPRECATED 기간 없이 ARCHIVED 또는 차단할 수 있다.

## 14.D 변경 요청과 영향 (VER-016 ~ VER-020)

### VER-016 - 변경 요청 기록
- **Priority:** Critical
- **Statement:** 승인 대상 변경에는 대상, 현재 버전·상태, 문제, 제안, 이유, 범위와 요청자를 기록해야 한다.
- **Rationale:** 변경의 필요성과 경계를 검토하려면 기준 정보가 필요하다.
- **Verification:** Change Request 필수 필드를 확인한다.
- **Exceptions:** 긴급 수정은 최소 기록으로 시작하고 안정화 후 보완한다.

### VER-017 - 영향 분석
- **Priority:** Critical
- **Statement:** 변경 전 관련 규칙, 문서, 프로젝트, 템플릿, 자동화, 데이터와 사용자 영향을 평가해야 한다.
- **Rationale:** 국소 변경처럼 보여도 하위 산출물에 연쇄 영향을 줄 수 있다.
- **Verification:** Impact Analysis와 참조 맵을 대조한다.
- **Exceptions:** 영향 없음이 명백한 오탈자는 대상 위치만 확인할 수 있다.

### VER-018 - 호환성 판정
- **Priority:** Critical
- **Statement:** 기존 입력, 출력, 규칙 참조와 사용 흐름이 유지되는지 호환 여부를 판정해야 한다.
- **Rationale:** 버전 증가와 마이그레이션 범위를 결정하는 핵심 근거다.
- **Verification:** Compatibility Matrix와 테스트 결과를 확인한다.
- **Exceptions:** 신규 독립 문서는 기존 호환성 대신 의존성 연결을 확인한다.

### VER-019 - 독립 변경 분리
- **Priority:** High
- **Statement:** 목적, 위험, 승인 또는 롤백 단위가 다른 변경은 하나의 릴리스에 불필요하게 묶지 않는다.
- **Rationale:** 큰 변경 묶음은 검토와 원인 추적, 선택적 롤백을 어렵게 한다.
- **Verification:** 변경 항목 간 의존성과 릴리스 목적을 검토한다.
- **Exceptions:** 동시에 배포해야만 정합성이 유지되는 변경은 하나로 묶는다.

### VER-020 - 범위 밖 아이디어 분리
- **Priority:** Critical
- **Statement:** 승인된 변경 목적과 무관한 새 아이디어를 같은 버전 작업에 추가하지 않는다.
- **Rationale:** 무단 범위 확장은 일정, QA와 승인 근거를 왜곡한다.
- **Verification:** Change Request와 최종 Diff를 비교한다.
- **Exceptions:** 안전·법률 위험은 별도 Critical 변경으로 즉시 보고한다.

## 14.E 검토와 승인 (VER-021 ~ VER-025)

### VER-021 - QA 증거 필수
- **Priority:** Critical
- **Statement:** APPROVED 또는 LOCKED 후보는 해당 정확한 버전에 대한 COR-005 QA 결과를 가져야 한다.
- **Rationale:** 다른 버전의 통과 결과는 현재 대상의 품질을 보장하지 않는다.
- **Verification:** QA 대상 해시와 승인 후보 해시를 비교한다.
- **Exceptions:** DRAFT·REVIEW 전환은 전체 QA 전에 가능하다.

### VER-022 - 검토 범위 완결성
- **Priority:** High
- **Statement:** 검토자는 변경 내용, 영향, 호환성, 의존성, 마이그레이션, 결함과 잔여 위험을 확인해야 한다.
- **Rationale:** 본문 Diff만 보면 운영 영향을 놓칠 수 있다.
- **Verification:** Review Checklist와 증거를 확인한다.
- **Exceptions:** Patch는 영향 없는 항목을 N/A로 기록할 수 있다.

### VER-023 - 승인 권한 확인
- **Priority:** Critical
- **Statement:** 상태 전환 승인자는 해당 문서·프로젝트와 변경 수준에 대한 권한을 가져야 한다.
- **Rationale:** 권한 없는 승인은 기준본 통제를 무효화한다.
- **Verification:** Owner·Delegation Register와 승인자를 대조한다.
- **Exceptions:** 긴급 대리 승인은 위임 근거와 사후 확인을 기록한다.

### VER-024 - 승인 대상 명시
- **Priority:** Critical
- **Statement:** 승인 기록에는 정확한 문서 ID, 버전, 해시, 상태 전환과 적용 범위를 명시해야 한다.
- **Rationale:** 모호한 승인은 다른 파일이나 범위에 잘못 적용될 수 있다.
- **Verification:** Approval Record의 대상 필드를 확인한다.
- **Exceptions:** 불변 릴리스 ID가 모든 파일을 식별하면 패키지 단위로 승인할 수 있다.

### VER-025 - 조건부 승인 통제
- **Priority:** High
- **Statement:** 조건부 승인에는 열린 항목, 위험, 사용 제한, 책임자, 기한과 재검토 조건을 기록해야 한다.
- **Rationale:** 조건 없는 승인은 미완료를 완료로 위장한다.
- **Verification:** Conditional Approval 필수 필드를 확인한다.
- **Exceptions:** Critical 결함은 조건부 승인으로 우회할 수 없다.

## 14.F LOCKED 통제 (VER-026 ~ VER-030)

### VER-026 - LOCKED 불변성
- **Priority:** Critical
- **Statement:** LOCKED 대상의 내용과 의미는 승인된 변경 요청과 새 버전 없이 수정하지 않는다.
- **Rationale:** 잠금본이 변하면 모든 참조와 검증 근거가 불안정해진다.
- **Verification:** Registry 해시와 현재 파일 해시를 비교한다.
- **Exceptions:** 저장 매체 복구는 동일 해시를 유지해야 한다.

### VER-027 - 잠금본 보존
- **Priority:** Critical
- **Statement:** 새 버전이 승인되어도 기존 LOCKED 버전과 승인·QA 증거를 이력으로 보존해야 한다.
- **Rationale:** 과거 프로젝트의 적용 기준과 결정을 재현해야 한다.
- **Verification:** Archive와 Approval Package 존재를 확인한다.
- **Exceptions:** 법적 삭제 의무가 있으면 식별 정보와 삭제 근거만 보존한다.

### VER-028 - 잠금 해제 절차
- **Priority:** Critical
- **Statement:** LOCKED 변경은 영향 분석, 새 버전, QA와 승인 절차를 다시 시작해야 한다.
- **Rationale:** 잠금본 직접 수정은 변경 통제를 우회한다.
- **Verification:** 새 Change Request와 버전 분기 기록을 확인한다.
- **Exceptions:** 없음.

### VER-029 - 실제 적용 증거
- **Priority:** High
- **Statement:** LOCKED 진입에 실제 적용이 요구된 경우 대상 프로젝트, 결과, 결함과 개선 반영을 기록해야 한다.
- **Rationale:** 문서 검토만으로 운영 적합성을 보장할 수 없다.
- **Verification:** Pilot 또는 Production Trial 기록을 확인한다.
- **Exceptions:** 사용 전 잠금이 법적으로 필요한 규격은 승인된 시뮬레이션으로 대체할 수 있다.

### VER-030 - 잠금 범위 명시
- **Priority:** Critical
- **Statement:** LOCKED 승인에는 잠긴 파일, 규칙, 섹션, 자산과 허용된 변경 범위를 명시해야 한다.
- **Rationale:** 일부 잠금과 전체 잠금을 혼동하면 필요한 수정도 차단하거나 무단 변경을 허용한다.
- **Verification:** Lock Scope와 패키지 매니페스트를 대조한다.
- **Exceptions:** 전체 패키지 해시로 범위가 완전히 식별되면 패키지 단위로 표시한다.

## 14.G 릴리스와 기준본 (VER-031 ~ VER-035)

### VER-031 - 단일 기준본 등록
- **Priority:** Critical
- **Statement:** 각 책임 단위와 적용 범위에는 현재 사용해야 할 하나의 기준 버전을 등록해야 한다.
- **Rationale:** 여러 기준본은 프로젝트마다 다른 규칙을 적용하게 한다.
- **Verification:** Canonical Registry의 중복 활성 항목을 확인한다.
- **Exceptions:** 병행 지원은 적용 대상과 기간을 분리해 각각 하나의 기준본을 둔다.

### VER-032 - 사전 릴리스 비우선
- **Priority:** High
- **Statement:** alpha, beta, rc 등 사전 릴리스는 명시적 시험 범위 밖에서 정식 기준본을 대체하지 않는다.
- **Rationale:** 검증 중 버전이 운영에 확산되는 것을 막는다.
- **Verification:** 운영 참조가 정식 버전을 가리키는지 확인한다.
- **Exceptions:** 승인된 Pilot은 사전 릴리스와 제한을 명시해 사용할 수 있다.

### VER-033 - 릴리스 패키지 완결성
- **Priority:** Critical
- **Statement:** 정식 릴리스에는 변경 이력, QA·승인 증거, 의존성, 마이그레이션, 검증값과 제한을 필요한 만큼 포함해야 한다.
- **Rationale:** 파일만으로는 안전한 적용과 감사가 어렵다.
- **Verification:** Release Manifest와 필수 구성요소를 대조한다.
- **Exceptions:** 영향 없는 Patch는 마이그레이션을 N/A로 표시할 수 있다.

### VER-034 - 기준본 전환 원자성
- **Priority:** Critical
- **Statement:** 기준본 전환 시 등록부, 참조 문서, 전달 패키지와 적용 안내가 서로 다른 버전을 가리키지 않게 해야 한다.
- **Rationale:** 부분 전환은 혼합 버전 사용을 만든다.
- **Verification:** 전환 후 모든 기준 참조를 검색해 비교한다.
- **Exceptions:** 단계적 전환은 대상 그룹과 기간을 명시한다.

### VER-035 - 지원 버전 명시
- **Priority:** High
- **Statement:** 여러 버전을 지원하면 적용 대상, 지원 수준, 종료일과 상호 차이를 명시해야 한다.
- **Rationale:** 지원 상태가 없으면 폐기본에 신규 의존성이 생길 수 있다.
- **Verification:** Support Matrix와 실제 프로젝트 참조를 대조한다.
- **Exceptions:** 단일 최신 버전만 지원하면 그 정책을 등록한다.

## 14.H 호환성·마이그레이션·의존성 (VER-036 ~ VER-040)

### VER-036 - 참조 호환성 검사
- **Priority:** Critical
- **Statement:** 규칙 ID, 문서 링크, 스키마, 입력·출력과 자동화 인터페이스의 호환성을 변경 전후 검사해야 한다.
- **Rationale:** 본문은 정상이어도 참조 계약이 깨질 수 있다.
- **Verification:** Compatibility Test와 참조 감사 결과를 확인한다.
- **Exceptions:** 독립 문구 Patch는 영향 없음 근거로 축약할 수 있다.

### VER-037 - 마이그레이션 안내
- **Priority:** Critical
- **Statement:** 기존 사용자의 변경이 필요하면 대상, 단계, 전제, 검증, 롤백과 기한을 설명하는 안내를 제공해야 한다.
- **Rationale:** 새 버전만 제공하면 안전한 전환을 재현할 수 없다.
- **Verification:** Migration Guide를 깨끗한 대상 환경에서 검토한다.
- **Exceptions:** 완전 호환 변경은 마이그레이션 불필요 근거를 기록한다.

### VER-038 - 의존 버전 정합
- **Priority:** Critical
- **Statement:** 상위·하위 문서, 프로젝트와 자동화가 요구하는 버전 범위를 충족하는 조합만 기준본으로 승인해야 한다.
- **Rationale:** 호환되지 않는 의존 버전은 운영 실패를 만든다.
- **Verification:** Dependency Matrix와 활성 기준본을 비교한다.
- **Exceptions:** 임시 호환 계층은 범위, 종료일과 위험을 명시한다.

### VER-039 - 마이그레이션 검증
- **Priority:** High
- **Statement:** 마이그레이션 후 핵심 기능, 데이터, 규칙 참조와 결과가 새 기준에 맞는지 검증해야 한다.
- **Rationale:** 절차 수행 완료와 결과 정확성은 다르다.
- **Verification:** Before/After 검사와 QA 결과를 확인한다.
- **Exceptions:** 문서 전용 변경은 참조·표현 정합성 검사로 대체할 수 있다.

### VER-040 - 혼합 버전 방지
- **Priority:** Critical
- **Statement:** 호환성이 확인되지 않은 서로 다른 버전의 문서, 규칙, 템플릿과 자동화를 하나의 기준 패키지에 섞지 않는다.
- **Rationale:** 혼합 구성은 재현할 수 없는 상태를 만든다.
- **Verification:** 패키지 매니페스트와 Dependency Lock을 확인한다.
- **Exceptions:** 호환성 시험 자체는 TEST 상태와 조합을 명시한다.

## 14.I 폐기·보관·롤백 (VER-041 ~ VER-045)

### VER-041 - DEPRECATED 대체 정보
- **Priority:** Critical
- **Statement:** DEPRECATED 버전에는 대체 버전, 폐기 이유, 전환 기한과 남은 지원 범위를 표시해야 한다.
- **Rationale:** 사용자는 무엇으로 언제 이동해야 하는지 알아야 한다.
- **Verification:** Deprecation Notice의 필수 필드를 확인한다.
- **Exceptions:** 즉시 보안 차단은 대체책과 긴급 조치를 우선 제공한다.

### VER-042 - ARCHIVED 운영 제외
- **Priority:** Critical
- **Statement:** ARCHIVED 버전은 운영 기준 등록부와 신규 프로젝트 기본값에서 제거해야 한다.
- **Rationale:** 이력본이 실수로 재사용되는 것을 막는다.
- **Verification:** 활성 Registry와 템플릿 참조를 확인한다.
- **Exceptions:** 과거 프로젝트 재현은 읽기 전용 이력 위치에서만 허용한다.

### VER-043 - 이력 보존
- **Priority:** High
- **Statement:** 폐기·보관된 버전의 파일, 해시, 효력 기간, 대체 관계와 승인 기록을 추적 가능하게 보존해야 한다.
- **Rationale:** 과거 결정과 프로젝트 기준을 감사할 수 있어야 한다.
- **Verification:** Archive Manifest와 파일 무결성을 확인한다.
- **Exceptions:** 보존 제한이 있으면 삭제 근거와 최소 메타데이터를 남긴다.

### VER-044 - 통제된 롤백
- **Priority:** Critical
- **Statement:** 롤백은 알려진 정상 버전, 대상 범위, 이유, 데이터·호환성 영향, QA와 승인에 연결해야 한다.
- **Rationale:** 단순 파일 교체는 더 큰 불일치와 데이터 손실을 만들 수 있다.
- **Verification:** Rollback Plan·Result와 기준본 등록부를 확인한다.
- **Exceptions:** 긴급 차단은 최소 안전 상태로 먼저 복구하고 기록과 정규 QA를 보완한다.

### VER-045 - 롤백 후 기준본 갱신
- **Priority:** Critical
- **Statement:** 롤백 완료 후 기준본, 의존성, 전달 링크와 상태 기록을 실제 활성 버전에 맞게 갱신해야 한다.
- **Rationale:** 시스템은 되돌렸지만 문서가 새 버전을 가리키는 분리를 막는다.
- **Verification:** 활성 산출물과 모든 기준 참조를 비교한다.
- **Exceptions:** 단계적 롤백은 대상 그룹별 활성 버전을 명시한다.

## 14.J 기록과 감사 (VER-046 ~ VER-050)

### VER-046 - 변경 이력 필수
- **Priority:** Critical
- **Statement:** 각 버전은 날짜, 변경 분류, 내용, 이유, 작성자, 관련 요청과 상태를 변경 이력에 기록해야 한다.
- **Rationale:** 버전 번호만으로는 무엇이 왜 바뀌었는지 알 수 없다.
- **Verification:** Change Log 필수 필드와 실제 Diff를 대조한다.
- **Exceptions:** 동일 목적의 소규모 Patch는 항목을 묶어 기록할 수 있다.

### VER-047 - 승인 기록 불변성
- **Priority:** Critical
- **Statement:** 승인 기록은 승인 후 알림 없이 수정하지 않고 정정은 새 이력으로 추가해야 한다.
- **Rationale:** 승인 근거가 사후 변경되면 감사 신뢰성이 사라진다.
- **Verification:** Approval Log의 변경 이력과 무결성을 확인한다.
- **Exceptions:** 개인정보 정정은 원래 결정 의미를 유지하며 사유를 남긴다.

### VER-048 - 기준본 등록부 최신성
- **Priority:** Critical
- **Statement:** 기준본 등록부는 상태 전환, 릴리스, 폐기, 롤백과 동시에 실제 활성 버전에 맞게 갱신해야 한다.
- **Rationale:** 오래된 등록부는 잘못된 버전 사용을 유도한다.
- **Verification:** Registry와 저장소·전달 위치의 활성 버전을 비교한다.
- **Exceptions:** 트랜잭션 지연은 전환 완료 전 상태로 표시한다.

### VER-049 - 버전 간 추적
- **Priority:** High
- **Statement:** 새 버전은 이전 버전, 대체·분기·병합 관계와 관련 변경 요청을 추적 가능하게 연결해야 한다.
- **Rationale:** 버전 계보가 있어야 변경 누락과 중복을 분석할 수 있다.
- **Verification:** Version Graph 또는 Change Log 링크를 확인한다.
- **Exceptions:** 최초 버전은 기원 문서와 작성 근거만 기록한다.

### VER-050 - 상태 허위 표시 금지
- **Priority:** Critical
- **Statement:** QA, 승인, 실제 적용 또는 잠금 조건을 충족하지 않은 버전을 APPROVED나 LOCKED로 표시하지 않는다.
- **Rationale:** 허위 상태는 미검증 기준을 운영에 확산시킨다.
- **Verification:** 상태별 필수 증거와 현재 메타데이터를 대조한다.
- **Exceptions:** 없음.

# 15. 표준 버전 수명주기

모든 JCOS 관리 대상은 아래 순서를 기본으로 한다.

1. **Draft** - 변경 목적, 범위, 대상과 초기 버전을 정하고 DRAFT로 작성한다.
2. **Assess** - 변경을 Major·Minor·Patch로 분류하고 영향·호환성·의존성을 평가한다.
3. **Review** - 검토 가능한 버전·해시를 고정하고 REVIEW에서 내용·QA·마이그레이션을 검토한다.
4. **Approve** - 지정 승인자가 정확한 대상과 범위를 명시해 APPROVED로 전환한다.
5. **Release** - 변경 이력, 패키지, 검증값과 기준본 등록부를 갱신해 배포한다.
6. **Validate** - 필요한 실제 적용과 운영 결과를 확인하고 결함을 반영한다.
7. **Lock** - 조건을 충족한 승인본을 명시적으로 LOCKED 운영 기준으로 고정한다.
8. **Retire** - 대체 시 DEPRECATED로 전환하고 지원 종료 후 ARCHIVED로 보존한다.

완료 전 QA는 COR-005, 파일 패키징·전달은 COR-006, 충돌·예외 결정은 COR-008을 따른다.

# 16. 준수 체크리스트

## 16.1 식별과 변경

- [ ] 관리 대상에 문서 ID, 세 자리 버전과 상태가 있다.
- [ ] 변경 요청에 목적, 범위, 이유와 대상 버전이 기록되었다.
- [ ] 변경을 Major, Minor 또는 Patch로 일관되게 분류했다.
- [ ] 영향, 호환성, 의존성과 마이그레이션 필요를 평가했다.
- [ ] 독립 변경과 범위 밖 아이디어를 별도 작업으로 분리했다.

## 16.2 검토와 승인

- [ ] REVIEW 대상의 정확한 버전과 해시가 고정되었다.
- [ ] 해당 버전에 대한 COR-005 QA 증거가 있다.
- [ ] 승인자에게 대상과 변경 수준의 권한이 있다.
- [ ] 승인 기록에 버전, 해시, 범위, 상태와 조건이 명시되었다.
- [ ] 침묵, 전달 또는 사용 시작을 승인으로 간주하지 않았다.

## 16.3 릴리스와 LOCKED

- [ ] 변경 이력, 의존성, 마이그레이션과 알려진 제한이 포함되었다.
- [ ] 하나의 활성 기준본과 적용 범위가 등록되었다.
- [ ] 관련 문서, 프로젝트와 전달 패키지의 버전 참조가 일치한다.
- [ ] LOCKED의 승인, QA, 실제 적용과 범위 조건을 충족했다.
- [ ] 기존 LOCKED 버전과 증거를 불변 이력으로 보존했다.

## 16.4 폐기와 기록

- [ ] DEPRECATED에 대체본, 전환 기한과 지원 범위가 있다.
- [ ] ARCHIVED가 신규 운영 기준에서 제거되었다.
- [ ] 롤백에 대상, 영향, QA, 승인과 기준본 갱신이 기록되었다.
- [ ] 변경·승인·기준본 등록부가 실제 파일·상태와 일치한다.
- [ ] 승인·공개된 버전 번호를 다른 내용에 재사용하지 않았다.
